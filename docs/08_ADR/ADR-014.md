# ADR-014 — Sustitución de Airtable como fuente operativa del conocimiento

## Contexto

`ADR-007` estableció Airtable como fuente operativa única del conocimiento y definió el flujo `Airtable → Scripts → Obsidian → GitHub`.

Ese modelo ya no corresponde al funcionamiento actual de FisioOS. Airtable ha dejado de formar parte del flujo operativo de creación, revisión y mantenimiento del conocimiento estructurado.

La evolución posterior del proyecto ha consolidado una arquitectura basada en archivos estructurados versionados mediante Git, mientras que los archivos binarios originales se conservan externamente cuando corresponde.

`ADR-008` establece que Google Drive actúa como repositorio de los archivos clínicos originales y que FisioOS conserva en Git el conocimiento estructurado, los metadatos y las relaciones necesarias para mantener su trazabilidad.

`ADR-013` aplica el mismo principio a los archivos multimedia pesados, manteniendo en Git sus derivados textuales y metadatos de referencia.

Persisten referencias históricas a Airtable en documentación y entidades creadas durante las primeras fases del proyecto. Estas referencias deben distinguirse entre procedencia histórica y dependencias operativas obsoletas, evitando eliminaciones o sustituciones indiscriminadas.

## Decisión

`ADR-014` sustituye la decisión operativa establecida en `ADR-007`.

Airtable deja de ser una fuente operativa, una dependencia y un paso obligatorio del flujo de FisioOS.

El conocimiento estructurado de FisioOS se mantiene en archivos versionados mediante Git. El repositorio Git constituye el registro versionado y auditable del conocimiento estructurado, sus metadatos, relaciones y documentación asociada.

Obsidian actúa como entorno principal de edición y navegación humana sobre esos archivos, sin constituir una base de datos independiente del repositorio.

GitHub mantiene la copia remota oficial del repositorio y su historial sincronizado.

Google Drive se utiliza para custodiar archivos binarios originales y otros recursos externalizados conforme a `ADR-008` y `ADR-013`. La existencia de un archivo en Drive no sustituye al registro estructurado correspondiente cuando este sea necesario para su trazabilidad dentro de FisioOS.

El flujo operativo general pasa a ser:

`Edición y validación → archivos estructurados de FisioOS → Git → GitHub`

Cuando existan binarios externos:

`Google Drive ↔ metadatos y referencias trazables en FisioOS`

Las referencias históricas a Airtable podrán conservarse únicamente cuando documenten la procedencia real de una entidad o una fase histórica del proyecto. No deberán interpretarse como una dependencia activa del sistema.

## Reglas

1. No se utilizará Airtable como paso obligatorio para crear, modificar, revisar o aprobar entidades de FisioOS.
2. Los cambios en el conocimiento estructurado deberán quedar registrados en archivos versionados mediante Git.
3. GitHub mantendrá la copia remota oficial y sincronizada del repositorio.
4. Obsidian podrá utilizarse como entorno de edición y navegación, pero los archivos del repositorio serán la representación persistente del conocimiento.
5. Google Drive custodiará los binarios y recursos externalizados que correspondan, siguiendo `ADR-008` y `ADR-013`.
6. Todo recurso externo que requiera trazabilidad deberá mantener en FisioOS los metadatos, identificadores o referencias necesarios para relacionarlo inequívocamente con su original.
7. Las referencias históricas a `Airtable`, `Airtable / Hombro.zip` o flujos equivalentes no se eliminarán automáticamente. Se revisarán de forma controlada para determinar si representan procedencia histórica o una dependencia operativa obsoleta.
8. Cuando una referencia a Airtable represente únicamente procedencia histórica, deberá expresarse de forma que no pueda confundirse con una fuente operativa activa.
9. La documentación que todavía describa Airtable como fuente operativa actual deberá actualizarse para ajustarse a esta decisión.
10. `ADR-007` se conserva como registro histórico de una decisión anterior, pero deja de definir la arquitectura operativa vigente de FisioOS.

## Consecuencias

- Airtable deja de formar parte de la arquitectura operativa vigente de FisioOS.
- La edición del conocimiento puede realizarse directamente sobre los archivos estructurados del repositorio, manteniendo revisión y control de versiones mediante Git.
- Git y GitHub proporcionan trazabilidad de los cambios realizados sobre el conocimiento estructurado.
- Google Drive mantiene su función como custodio externo de los archivos binarios definidos en `ADR-008` y `ADR-013`.
- Las referencias históricas a Airtable podrán mantenerse cuando sean necesarias para preservar la procedencia de entidades antiguas, pero deberán quedar claramente identificadas como históricas.
- La documentación heredada que presente Airtable como componente activo deberá revisarse progresivamente.
- La migración de referencias históricas se realizará de forma controlada y separada de la creación de nuevo conocimiento clínico.
- Esta decisión no modifica por sí sola la procedencia histórica de las entidades existentes ni autoriza reemplazos masivos sin revisión individual.
